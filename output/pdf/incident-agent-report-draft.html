1. 진행 사항 소개

기존 Base AI Agent의 조사·검색·검증 흐름을 개선해, 확보한 자료에 맞는 장애 대응 답변을 생성하도록 구성했다.

출발점: 확인하지 않은 사실을 단정하는 답변

CPU가 높다는 한 번의 관측만으로 지속 고부하를 단정하고, 조회하지 않은 로그를 분석했다고 설명했다. 미등록 서비스를 다른 서비스로 대신 조사하는 문제도 있었다.

추가·수정한 기능

  1. 대상·근거 확인: 미등록 대상의 임의 대체를 막고 로그·시계열·배포 자료의 제공 여부를 구분했다.
  2. RAG: 키워드 기반 단일 문서 선택을 벡터 유사도 기반 다중 Runbook 검색으로 확장했다.
  3. 선택적 멀티에이전트: 지표·로그·Runbook 분석을 분리하고 필요한 역할만 병렬 호출했다.
  4. 검증·평가: 의미 검증과 Fallback을 추가하고, 고정 평가 자료 및 동일 기준 재채점을 구성했다.

@mcp.tool()
def get_diagnostic_evidence(system_name: str) -> dict:
    """명시적 모의 진단 자료 조회. 자료 미제공은 정상 또는 이상 없음이 아니다."""

    if system_name not in registry:
        raise ValueError("System not registered")
    path = DATA_DIR / "diagnostic_evidence.json"
    data = json.loads(path.read_text()) if path.exists() else {}
    source = data.get(system_name, {})
    return {
        "system_name": system_name,

# 추가: 유사도 기준 미달 문서는 제외하고 검색어당 상위 후보를 제한
def select(self, ranked):
    if not ranked or ranked[0]["score"] < self.threshold:
        return []
    cutoff = max(self.threshold, ranked[0]["score"]-self.margin)
    return [d for d in ranked[:self.top_k] if d["score"] >= cutoff]
agent/retrieval.py · 124-131행
# 추가: 검색어별 후보를 합쳐 문서 ID로 중복 제거하고 다중 Runbook을 반환
async def search(self, queries):
    rankings = await self.rank(queries)
    unique = {}
    for ranking in rankings:
        for doc in self.select(ranking):
            if doc["id"] not in unique or doc["score"] > unique[doc["id"]]["score"]:
                unique[doc["id"]] = doc
    return sorted(unique.values(), key=lambda d: (-d["score"],d["id"]))

현재 설정은 검색어당 top_k=1, threshold=0.25, margin=0.12다. 검색어가 여러 개이므로 최종 문서는 여러 개일 수 있다. SQLite에 문서·벡터를 저장하고 문서 해시나 모델이 바뀐 문서만 다시 임베딩한다.

2. 사용한 기술 요소 · 적용 범위

과제의 8개 개선 항목적용 내용

초기 99회 모델 호출은 총 토큰과 가상 비용만 저장했다. 입력·출력·캐시별 사용량은 현재 버전부터 기록했으므로, 보존된 초기 기록만으로 동일 방식의 비용을 복원할 수 없다. 가상 비용과 입력·출력별 추정 비용을 교차 비교할 수 없으며, 현재 추정 비용에는 문서 최초 임베딩 비용이 포함되지 않는다.

측정 조건과 해석

초기 2026.10.20, 현재 2026.10.21 실행 기록이다. 질문·반복·턴, 데이터 매니페스트와 Runbook 해시가 일치하고, 공통 조회 대상의 모니터링 값도 동일했다. 모델 구성은 gpt-4o-mini/gpt-4o, temperature=0이며 무작위 지연·도구 오류 주입이 없는 고정 MCP를 사용했다. p95는 nearest-rank 방식이다.

전체 중앙값은 비슷하지만 긴 응답 구간과 총 토큰은 증가했다. 실행 시점·API 응답 편차가 있으므로 속도 차이는 보존 기록의 관측 결과로 해석한다. 모의 CPU 수치의 하락을 측정한 결과가 아니다.

이후 반영하고 싶은 개선 포인트

5. 이후 반영하고 싶은 개선 포인트

① 개발용 질문과 최종 평가용 질문 분리

같은 10개 사례를 보고 프롬프트·검색·분기를 수정했으므로 과적합 위험이 있다. 현재 코드를 고정한 뒤, 사용하지 않은 서비스 조합·임계값·자료 누락·충돌 사례로 초기와 현재를 비교해야 한다. 질문 표현만 바꾸는 평가로는 충분하지 않다.

② LLM 평가와 결정적 검사를 함께 사용

동일 모델과 지침을 사용해도 평가의 정확성이 보장되지는 않았다. 수치 비교·대상 일치·근거 ID는 코드로 검사하고, 인과관계·자료 부재·조치 전제는 원문과 대조해야 한다. 자동 점수와 검토 결과는 구분해 보존한다.

③ 검색 정밀도와 비용·지연의 균형

다중 문서 검색은 누락을 줄였지만 불필요한 문서를 포함했다. 선택적 전문가 호출과 출력 축소를 적용했어도 최초 버전 대비 토큰은 2.61배, p95 지연은 36.8% 증가했다. 관련성 필터와 입력 축소는 새로운 평가 사례에서 품질 저하 여부와 함께 검증해야 한다.

④ 초기·현재 비용 계측 통일

초기 기록에는 입력·출력·캐시 토큰이 없어 현재의 비용 추정 방식과 직접 비교할 수 없다. 최초 그래프 동작은 보존하고 계측만 보강해 다시 측정하되, 기존 Before 기록과 새 실행 결과를 구분해야 한다.

⑤ 실제 조치·장기 대화의 후속 설계

현재는 조치 권고 중심이며 사람 승인과 장기 대화 요약은 미구현이다. 실제 재시작·증설에 연결할 경우 권한·승인·실행 결과 확인을, 장기 대화에는 요약 시 정보 손실과 비용 감소를 함께 설계해야 한다.
