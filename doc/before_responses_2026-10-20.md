# 장애 진단 에이전트 개선 전 응답 기록

답변 품질 개선 전 비교 자료다. 아래 응답은 대화에 수집된 원문을 보존한 것으로, 내용의 사실성을 보증하거나 권장 조치로 승인한 문서가 아니다. 평가와 개선 기준은 [질문별 평가 기준](./regression_evaluation_criteria.md)에 별도로 작성했다.

## 수집 조건

- 수집일: 2026-10-20, Asia/Seoul. 정확한 실행 시각은 미수집.
- 질문 출처: [regression_test_queries.md](./regression_test_queries.md).
- 수집 경로: `http://localhost:8600/` 프론트엔드에 직접 입력하고 화면의 최종 응답 확인.
- 화면 표시 모델: `openai:gpt-4o-mini/openai:gpt-4o`.
- 10개 테스트 항목, 총 11개 입력과 응답. 10번은 이름 입력과 후속 질문 두 턴으로 구성.
- 새로 연 화면에서 같은 대화로 1번부터 순차 실행. 서버 재시작은 하지 않았다.
- 모니터링 입력은 기존 난수 기반 모의 데이터. 이번 수집에서 고정하지 않았다.
- 응답 시간, 토큰 사용량, 실제 비용, 실행별 도구 반환 원문, LangSmith 실행 ID, 당시 코드 커밋: 미수집.
- 코드 및 `.env` 파일을 변경하지 않고 수집했다. `.env`에는 접근하지 않았다.
- 아래 기록은 과거 화면 관찰을 옮긴 정성적 Before 자료다. 정확한 수치 인용률이나 성능 개선율을 계산할 짝지어진 정량 실험은 아니다.
- 진행 이벤트는 응답 원문과 분리해 일부만 기록했다. 화면에 특정 이벤트가 없었다는 이유만으로 내부 노드 미실행을 단정하지 않는다.

## 1번 결제 서비스 CPU 급증

질문: payments-service 결제 응답이 느려지고 CPU가 치솟았어요, 원인 확인해주세요

관찰된 진행: payments-service 모니터링 조회, cpu-spike 매뉴얼 조회, 초안 1회, 검수 통과.

### 최종 응답 원문

```text
1) 모니터링 결과, payments-service의 상태가 저하되었으며 CPU 사용률이 94.6%로 높게 나타났습니다. 메모리 사용률은 56.8%이며, 관련 알림으로는 'CPU 91% (threshold 80%)'와 'payments-service-3 instance responding slow'가 있습니다.

2) 최근 로그를 분석한 결과, 반복 호출이나 배치 작업 중복 실행과 같은 특정 요청 패턴은 발견되지 않았습니다.

3) CPU 사용률이 90%를 넘고 지속되고 있으므로, 오토스케일링 그룹에서 인스턴스를 추가로 띄워 부하를 분산시키는 조치를 권장합니다. 추가로, 문제가 특정 배포 직후 발생한 것이 아니라면, 배포 롤백은 필요하지 않습니다. 정상화 후에는 프로파일링을 통해 핫스팟 코드를 식별하고 최적화 작업을 진행해야 합니다.
```

## 2번 캐시 서비스 메모리 증가

질문: cache-service 메모리 사용률이 계속 올라가고 있어요

관찰된 진행: cache-service 모니터링 조회, memory-leak 매뉴얼 조회, 초안 1회, 검수 통과.

### 최종 응답 원문

```text
1) 현재 cache-service의 메모리 사용률이 88.7%로 높으며, 상태가 'degraded'로 표시되고 있습니다. 알림으로는 'memory usage climbing steadily over 6h'와 'heap near limit'이 감지되었습니다.

2) 메모리 사용률이 90%에 근접하고 있어 OOM(Out Of Memory) 상황을 방지하기 위해 해당 프로세스를 즉시 재시작하는 것이 필요합니다. 이는 임시 조치임을 기록해두어야 합니다.

3) 이후, 힙 덤프 또는 프로파일링 도구를 사용하여 어떤 객체가 계속 쌓이고 있는지 확인해야 합니다. 현재까지의 패턴 분석에서는 특이한 패턴이 발견되지 않았습니다. 따라서, 캐시 무제한 증가, 커넥션 미반환, 이벤트 리스너 중복 등록 같은 패턴이 최근 배포에 있었는지 추가 점검이 필요합니다. 원인이 된 배포가 발견되면 롤백을 고려하고, 컨테이너 메모리 상한선을 재확인하여 재발 시 더 빨리 감지되도록 조정해야 합니다.
```

## 3번 로그 서비스 디스크 부족

질문: log-service 디스크 공간이 부족하다는 알림이 왔어요

관찰된 진행: log-service 모니터링 조회, disk-full 매뉴얼 조회, 초안 1회, 검수 통과.

### 최종 응답 원문

```text
1) 모니터링 결과, log-service의 디스크 사용률이 95%로 임계 수준(90% 이상)을 초과하여 상태가 'degraded'로 나타났습니다.

2) 디스크 공간 확보를 위해 로그 파일, 임시 파일, 오래된 백업 파일 등 안전하게 삭제 가능한 항목을 정리하여 즉시 여유 공간을 확보해야 합니다.

3) 특정 프로세스가 비정상적으로 로그를 쌓고 있는 경우, 로그 레벨을 낮추거나 로그 로테이션 주기를 단축하여 로그 생성량을 줄이는 조치를 고려해야 합니다. 임시 조치로도 부족할 경우, 볼륨 확장이나 추가 스토리지 연결을 검토해야 합니다. 정상화 후에는 로그 보존 정책과 디스크 사용률 알림 임계값을 재검토하여 조기에 문제를 감지할 수 있도록 조정해야 합니다.
```

## 4번 서비스 간 타임아웃

질문: gateway-service에서 payments-service로 가는 요청이 타임아웃 나고 있어요

관찰된 진행: gateway-service와 payments-service 모니터링 조회, cpu-spike 매뉴얼만 조회, 초안 1회, 검수 통과.

### 최종 응답 원문

```text
1) 현재 gateway-service에서 payments-service로의 요청이 타임아웃되는 문제는 주로 두 서비스 모두에서 발생하는 성능 저하와 관련이 있습니다. gateway-service는 'upstream timeout to payments-service (504)'와 'network packet loss 3%' 알림을 받고 있으며, payments-service는 CPU 사용률이 91.7%로 높고 'payments-service-3 instance responding slow' 알림을 받고 있습니다.

2) payments-service의 CPU 사용률이 91.7%로 매우 높아, 오토스케일링 그룹에서 인스턴스를 추가하여 부하를 분산시키는 것이 필요합니다. 이는 runbook의 절차에 따라 CPU가 90%를 넘고 지속될 경우 수행해야 하는 조치입니다.

3) 문제 해결을 위해 payments-service의 인스턴스를 추가하여 부하를 분산시키고, 이후 정상화되면 프로파일링 결과를 바탕으로 핫스팟 코드를 식별하여 최적화 작업을 진행해야 합니다. 추가적으로, 네트워크 패킷 손실 문제도 함께 조사하여 해결해야 합니다.
```

## 5번 두 서비스 지표 확인

질문: web-01 CPU 급증, auth-service 커넥션 풀도 같이 확인해줘

관찰된 진행: web-01과 auth-service 모니터링 조회, high-latency 매뉴얼 조회, 초안 1회, 검수 통과.

### 최종 응답 원문

```text
1) web-01의 상태는 'healthy'이며, CPU 사용률은 41.9%로 정상 범위 내에 있습니다. 메모리 사용률은 51.9%이며, 관련 알림은 없습니다.

2) auth-service의 상태는 'degraded'로, CPU 사용률은 78.7%입니다. 메모리 사용률은 61.4%이며, 두 건의 알림이 있습니다: 'p95 latency 2.4s (threshold 1.0s)'와 'connection pool 92% used'.

3) 대응 절차에 따라, auth-service의 커넥션 풀 사용률이 92%로 90%를 초과하므로, 풀 크기를 늘리거나 느린 쿼리/외부 호출에 타임아웃을 설정해야 합니다. 또한, p95 지연시간이 임계치(1.0s)를 초과하므로, 캐시 계층 또는 읽기 복제본으로 트래픽을 분산하는 조치를 고려해야 합니다. 정상화 후에는 느린 쿼리 로그를 분석하여 근본 원인을 문서화하고 후속 최적화 티켓을 등록해야 합니다.
```

## 6번 공통 원인 분석

질문: payments-service랑 cache-service 둘 다 저하됐는데 공통 원인이 있는지 분석해줘

관찰된 진행: 할 일 3가지 계획, 두 서비스 모니터링 조회, cpu-spike 매뉴얼만 조회, 초안 1회, 검수 통과. 분석 노드의 실제 입출력 원문은 미수집.

### 최종 응답 원문

```text
1) payments-service의 상태 저하는 CPU 사용률이 93.5%로 높고, 인스턴스 응답이 느린 것이 원인으로 보입니다. 알림으로는 'CPU 91% (threshold 80%)'와 'payments-service-3 instance responding slow'가 발생했습니다.

2) cache-service의 상태 저하는 메모리 사용률이 90.3%로 높고, 'memory usage climbing steadily over 6h'와 'heap near limit' 알림이 발생했습니다.

3) 두 서비스의 공통 원인으로는 발견된 특이 패턴이 없으며, 각각 CPU와 메모리 사용률 문제로 인한 상태 저하로 보입니다. 따라서, 각각의 문제에 대해 별도로 대응이 필요합니다. payments-service는 CPU 부하 분산을 위해 오토스케일링을 고려하고, cache-service는 메모리 사용 최적화가 필요합니다.
```

1) 모니터링 결과 payments-service의 상태가 저하되었으며, CPU 사용률이 92.5%로 높고 메모리 사용률은 55.8%입니다. 알림으로는 'CPU 91% (threshold 80%)'와 'payments-service-3 instance responding slow'가 발생했습니다.

3) CPU 사용률이 90%를 넘고 지속되고 있으므로, 오토스케일링 그룹에서 인스턴스를 한 대 더 추가하여 부하를 분산시키는 조치를 권장합니다. 추가로, 문제가 특정 배포 직후 시작된 것이 아니라면, 배포 롤백은 필요하지 않습니다. 정상화 후에는 프로파일링 결과를 바탕으로 핫스팟 코드를 식별하여 최적화 작업을 진행해야 합니다.
