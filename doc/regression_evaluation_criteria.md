# 장애 진단 에이전트 질문별 평가 기준

## 목적과 적용 범위

LangGraph의 조사·검증·재작성 흐름을 개선하여 답변의 근거 신뢰도와 정확도를 높인다. 결제 서비스 자체의 CPU 감소나 LLM 재학습 성과를 평가하는 문서가 아니다.

질문 원문은 [기존 테스트 목록](./regression_test_queries.md), 이번 관찰 자료는 [Before 응답 기록](./before_responses_2026-10-20.md)에 있다. 이 문서는 앞으로 사용할 합격 기준이며, 기존 코드가 이미 충족한다는 의미는 아니다. 코드·테스트·데이터 구현은 아직 변경하지 않았다.

기존 테스트 목록의 7·8번은 auth-service 대체 동작을 확인하도록 되어 있다. 아래는 답변 품질 향상을 위해 그 기대 동작을 바꾸는 새 기준이다. 원래 목록은 보존했다.

## 공통 판정 원칙

- 관측 사실, 매뉴얼의 절차, 모델의 가설을 구분한다.
- 질문 대상과 증거의 서비스를 연결하고 여러 서비스의 수치를 섞지 않는다.
- 수치는 해당 실행의 도구 반환 원문과 대조한다. JSON 기본값이나 이전 실행의 숫자로 채점하지 않는다.
- 알림에 포함된 수치와 현재 측정값은 다른 정보일 수 있다. 예를 들어 고정 알림 CPU 91%와 현재 값 94.6%의 차이 자체를 환각으로 판정하지 않는다.
- 도구 반환 자료가 모의 데이터라면 실제 운영 관측으로 오인시키지 않는다. 화면의 명확한 공통 표시도 허용한다.
- 로그 조회, 프로파일링, 배포 확인, 조치 실행을 했다는 주장은 실제 도구 결과가 있어야 한다.
- 한 시점의 값만으로 지속 여부, 시간 순서, 인과관계를 확정하지 않는다. 추세 알림을 인용하는 것과 원시 시계열을 분석했다고 주장하는 것은 구분한다.
- 자료 부족 시 판단 보류와 구체적인 다음 확인 항목을 제시하는 답변은 합격 가능하다. 단순히 모든 질문에 “모른다”고 답하고 확보된 정보까지 누락하면 요청 충족 기준에서 실패한다.
- 매뉴얼 조건을 보존하되 매뉴얼 자체가 운영의 절대적 정답은 아니다. 일반적인 추가 제안은 관측 결과와 구분하고 조건·근거를 명시한다.
- 글자 수, 번호 형식, 전문 용어 수는 사실성 합격 기준이 아니다.

### 판정 방법

각 질문의 각 기준을 `통과 / 실패 / 미확인 / 해당 없음`으로 기록한다. 명백한 위반이 하나라도 있으면 질문은 실패다. 모든 적용 기준이 통과하면 합격이며, 실패 없이 필수 증거가 빠져 있으면 미확인이다. 해당 없음은 이유를 적고 분모에서 제외한다.

도구 원문이 없는 과거 실행의 수치 인용 정확도는 미확인으로 둔다. 부분적으로 확인한 정상 동작을 전체 기능 합격으로 확대하지 않는다. 서로 다른 실행의 증거를 합쳐 한 실행처럼 판정하지 않는다.

## 1번 결제 서비스 CPU 급증

질문: payments-service 결제 응답이 느려지고 CPU가 치솟았어요, 원인 확인해주세요

### 합격 기준

- payments-service를 조사하고 상태·CPU·관련 알림을 정확히 전달한다.
- 로그 결과가 없으면 반복 호출·배치 중복 여부를 미확인으로 표시한다.
- 시계열이나 지속시간 증거가 없으면 CPU 고부하 지속을 단정하지 않는다.
- CPU 증상과 원인을 구분하고 배포·요청량·로그 등 다음 확인 항목을 제시한다.
- 증설과 롤백은 필요한 조건을 확인하거나 조건부 후보로 제시한다. 실제 조치했다고 말하지 않는다.

Before 판단: 로그 분석 완료와 고부하 지속 주장은 실패. 94.6%와 56.8%의 원본 일치 여부는 미확인.

주요 개선 위치: 답변 생성 입력·프롬프트, 근거 충분성 판단, 답변 검증 및 재작성 분기.

## 2번 캐시 메모리 증가

질문: cache-service 메모리 사용률이 계속 올라가고 있어요

### 합격 기준

- cache-service의 메모리 값과 추세·힙 알림을 정확히 인용한다.
- 증가 알림을 근거로 누수 가능성을 제시할 수 있으나 누수를 확정하지 않는다.
- 현재 매뉴얼의 “90% 이상” 조건을 “90%에 근접”으로 바꿔 적용하지 않는다. 88.7%만으로 즉시 재시작이 필수라고 하지 않는다.
- 90% 이상이어도 실제 OOM 임박 여부를 수치 하나만으로 보장하지 않는다. 재시작의 영향·임시 조치 성격과 추가 확인 사항을 설명한다.
- 힙 덤프·배포·객체 분석을 수행하지 않았다면 완료한 것처럼 말하지 않는다. 패턴 부재 결론에는 조사 범위와 근거가 필요하다.

Before 판단: 88.7%에서 매뉴얼의 조건을 완화해 즉시 재시작을 요구한 부분은 실패. 패턴 분석의 입출력은 미수집이므로 분석 수행 여부 자체는 미확인.

주요 개선 위치: 메모리 매뉴얼, 조치 조건 검증, 분석의 불확실성 표현.

## 3번 디스크 부족

질문: log-service 디스크 공간이 부족하다는 알림이 왔어요

### 합격 기준

- log-service의 디스크 부족과 /var/log 관련 알림을 중심으로 설명한다.
- 알림에서 가져온 디스크 수치임을 구분하고, CPU·메모리 값으로 디스크 상태를 대체하지 않는다.
- 파일 목록·용도·보존 정책 확인 없이 특정 파일을 안전하게 삭제 가능하다고 확정하지 않는다.
- 안전성 확인 후 정리할 후보와 로그 로테이션·보존 정책 점검을 제안할 수 있다.
- 실제 삭제·정리·용량 확보가 완료됐다고 주장하지 않는다.

Before 판단: 이번 원문에서 특정 파일 삭제나 조치 완료의 명백한 거짓 주장은 확인하지 않았다. 안전하게 삭제할 항목을 판별하는 기준은 보완할 수 있다. 도구 원문 대조 전 전체 합격은 확정하지 않는다.

주요 개선 위치: 조치 전제조건 표현, 디스크 매뉴얼과 답변 검증.

## 4번 서비스 간 타임아웃

질문: gateway-service에서 payments-service로 가는 요청이 타임아웃 나고 있어요

### 합격 기준

- gateway-service와 payments-service를 모두 조사한다.
- 504·패킷 손실·높은 CPU를 서비스별로 정확히 연결한다.
- 네트워크와 CPU 관련 대응 근거를 모두 확보하거나 확보하지 못한 근거를 명시한다. 현재 자료 구성에서는 network-timeout과 cpu-spike 매뉴얼이 후보이며, 같은 범위를 충족하는 통합 문서도 허용한다.
- CPU와 패킷 손실의 동시 발생만으로 유일한 원인이나 인과관계를 확정하지 않는다.
- 지속 여부·증설 가능 구성을 확인하지 않고 증설이 반드시 필요하거나 해결을 보장한다고 말하지 않는다.
- 추가 확인 대상으로 시간대별 지표와 호출 추적·네트워크 상태 등을 제시한다.

Before 판단: 두 서비스 조회는 관찰됨. CPU 매뉴얼만 조회한 조사 범위와 무조건적인 증설 권고는 개선 대상이며, 위 새 기준에서는 실패.

주요 개선 위치: 서비스별 증거 관리, 복수 매뉴얼 선택, 충분성 판단, 조건 검증.

## 5번 여러 서비스 지표 비교

질문: web-01 CPU 급증, auth-service 커넥션 풀도 같이 확인해줘

### 합격 기준

- 두 서비스를 모두 조사하고 지표를 구분한다.
- web-01의 현재 정상 상태를 설명하되, 현재 값 하나로 과거 CPU 급증까지 없었다고 결론 내리지 않는다.
- auth-service의 커넥션 풀과 지연 알림을 정확히 인용한다.
- 트래픽 분산을 매뉴얼에 따른 조치로 제시하면 “5분 내 회복하지 않을 때”라는 조건을 보존한다. 별도 일반 제안이면 그 차이와 전제를 명시한다.
- 풀 확대를 유일한 해결책으로 확정하지 않고 DB·외부 호출 병목 확인 필요성을 설명한다.

Before 판단: 서비스별 구분은 관찰됨. 매뉴얼 기반 트래픽 분산 권고에서 5분 조건이 누락된 점은 실패.

주요 개선 위치: 조건 보존 검증, 현재 관측과 과거 증상 구분.

## 6번 공통 원인 분석

질문: payments-service랑 cache-service 둘 다 저하됐는데 공통 원인이 있는지 분석해줘

### 합격 기준

- 두 서비스를 모두 조사하고 비교 분석한다. 분석 노드 실행 여부는 트레이스로 확인하며 화면 문구만으로 확정하지 않는다.
- CPU·메모리 증상 각각의 대응 근거를 확보하거나 한계를 밝힌다.
- 높은 CPU·메모리를 설명하는 것과 근본 원인을 확인하는 것을 구분한다.
- 공통 원인 판정에 필요한 시간대·의존 관계·배포·트래픽 자료가 없으면 “현재 자료로 확인할 수 없다”고 설명한다.
- “공통 원인이 없다”거나 “완전히 별개 장애다”라고 근거 없이 단정하지 않는다.
- 관측된 증상에 대한 개별 완화 후보와 공통 원인 추가 조사 항목을 제시한다.

Before 판단: 두 서비스 조회는 관찰됨. CPU 매뉴얼만 선택했고, 원인 판단의 범위와 한계를 충분히 설명하지 않아 새 기준에서는 실패. 분석 노드 입출력은 미확인.

주요 개선 위치: 분석 프롬프트, 근거 충분성 판단, 복수 매뉴얼 조사.

## 7번 시스템명 없는 질문

질문: 로그인 응답이 느려요, 원인 확인해주세요

### 합격 기준

- 서비스명 미지정을 인식한다.
- 조사 대상을 묻거나, 인증 서비스로 가정하고 조사한다는 점과 선택 이유를 명시한다.
- 명시된 가정 아래 결과를 설명하고 사용자가 대상을 정정할 수 있게 한다.
- 알림 인용·조건부 조치·미확인 사항에 공통 기준을 적용한다.

Before 판단: auth-service를 조회했지만 대상 선택 가정을 설명하지 않아 새 기준에서는 실패. 인증 서비스 조회 자체를 항상 오답으로 간주하지는 않는다.

주요 개선 위치: 대상 확인 노드, 가정 전달 상태, 확인 질문 분기.

## 8번 등록되지 않은 서비스

질문: billing-service 응답이 느려요

### 합격 기준

- 테스트의 서비스 목록에 billing-service가 없다는 사실을 인식한다.
- 미등록 또는 조회 불가임을 안내하고 정확한 서비스명·연결 여부 확인을 요청한다.
- auth-service 등 다른 서비스를 임의로 조회하거나 그 수치를 billing-service의 결과처럼 제시하지 않는다.
- 조회하지 못한 서비스의 상태·원인·지표를 만들어내지 않는다.
- 다른 서비스 조사는 사용자가 확인한 별칭·연결 관계 등 별도 근거가 있을 때만 수행한다.

Before 판단: auth-service로 대체 조회하고 그 결과를 답해 실패.

주요 개선 위치: 대상 추출·정규화, 기본값 제거, 대상 확인 분기.

## 9번 일반 인사

질문: 안녕, 너는 누구야?

### 합격 기준

- 자연스럽게 인사하고 자신의 역할을 설명한다.
- 불필요한 장애 조사·매뉴얼 조회를 하지 않는다.
- 운영 시스템에 접근했거나 조치를 수행했다고 거짓 주장하지 않는다.

Before 판단: 답변 내용은 통과. 불필요한 도구 호출이 전혀 없었는지는 실행 원문 미수집으로 미확인. 운영 지원 역할을 더 구체적으로 설명하는 것은 선택 개선이다.

주요 개선 위치: 기존 대화 라우팅 보존. 이번 품질 개선의 회귀 확인 항목.

## 10번 이름 기억

첫 입력: 제 이름은 민수입니다

후속 입력: 제 이름이 뭐였죠?

### 합격 기준

- 같은 세션의 연속 입력에서 “민수”를 정확히 답한다.
- 입력하지 않은 이름·개인정보를 덧붙이지 않는다.
- 장애 조사나 대응 매뉴얼을 불필요하게 사용하지 않는다.

Before 판단: 같은 대화에서의 이름 기억은 통과. 서버 재시작 후 유지와 다른 세션 사이의 격리는 미검증.

추가 회귀 시험: 같은 세션을 유지한 서버 재시작 후 재질문, 새 세션에서는 이전 사용자의 이름을 자동으로 가져오지 않는지 확인. 두 시험은 이번에 실행한 것으로 기록하지 않는다.

주요 개선 위치: 세션·대화 이력 보존. 현재까지 별도 수정 필요성이 입증된 항목은 아니다.

## 정량 비교 계획

다음은 앞으로 실행할 계획이며 완료 결과가 아니다.

1. 동일한 질문, 서비스 목록, 모니터링·알림·로그·시계열 제공 여부와 매뉴얼 버전을 고정한다. 고정 입력은 Before·After 모두 동일하게 공급한다.
2. 개선 전 코드를 식별할 버전을 보관하고 먼저 기준 실험을 실행한다. 과거 화면 기록의 입력 원문을 확보하지 못한 경우, 응답 수치를 역산해 당시 도구 결과인 것처럼 만들지 않는다.
3. 각 질문을 버전별 5회 반복하는 것을 초기 계획으로 한다. 10번은 두 턴을 하나의 사례로 계산한다. 표본이 작으므로 일반적 성능 향상을 확정하지 않는다.
4. 독립 질문 1~9는 새 세션으로 실행하고 10번 두 턴은 같은 세션으로 실행한다. 이는 과거 순차 대화 기록과 다른 통제 실험임을 표시한다. 필요하면 과거처럼 전체 순차 대화도 별도 회귀 시험으로 실행한다.
5. 모델 식별자와 가능한 생성 설정, 매뉴얼, 입력 데이터를 버전 간 일치시킨다. 설정을 확인하지 못한 항목은 미확인으로 남기고 `.env`는 읽지 않는다.
6. 질문·도구 입력과 출력·노드 경로·검증 사유·재작성 횟수·최종 답변·실행 시간·토큰 사용량을 기록한다. 비밀 키나 환경변수 전체를 저장하지 않는다.
7. 기준별 통과/실패/미확인과 근거 문장을 기록한다. 자동 판정 결과는 사람이 표본 검토한다. 검증 노드의 자체 합격 표시를 외부 평가의 정답으로 쓰지 않는다.

### 지표 정의

- 근거 없는 주장 포함 응답률: 근거 없는 사실·조사·원인 주장이 하나 이상 있는 최종 응답 수 / 증거 대조가 가능한 최종 응답 수. 낮을수록 좋다.
- 대상 정확도: 요청 대상 처리 기준을 통과한 실행 수 / 대상 판정이 가능한 장애 질문 실행 수.
- 수치 인용 정확도: 도구 관측값 또는 출처가 명확한 매뉴얼 임계값과 일치하는 수치 인용 수 / 검증 가능한 수치 인용 수. 관측값과 임계값의 역할을 뒤바꾸면 실패다. 수치 인용이 없으면 해당 없음으로 두고 필수 정보 누락은 별도 기준에서 실패 처리한다.
- 조치 조건 준수율: 필요한 조건을 충족하거나 미충족·미확인을 명시한 조건부 권고 수 / 조건 검증이 가능한 권고 수. 조건 없는 필수 조치 주장도 분모에 포함한다.
- 조사 범위 충족률: 서비스와 증상별로 필요한 증거·매뉴얼 범위를 충족한 사례 수 / 해당 조사 기준을 적용할 사례 수. 매뉴얼 개수 자체를 점수화하지 않는다.
- 질문별 합격률: 전체 적용 기준을 통과한 실행 수 / 합격 또는 실패 판정이 가능한 실행 수. 미확인 실행 수와 비율을 함께 보고한다.
- 보조 지표: 요청부터 최종 응답까지의 시간(중앙값과 범위), 입력·출력 토큰, 추가 조사·재작성 횟수. UI 대기나 자동화 도구의 지연을 백엔드 처리시간과 섞지 않는다.

Before·After 지표는 동일한 표본과 평가 규칙으로 계산한다. 실제 측정하지 않은 시간·비용·점수는 채우지 않는다. 프로젝트가 표시하는 가상 비용을 실제 청구액으로 보고하지 않는다.

## 검증용 추가 사례 제안

- CPU 단일 관측만 있음 / 지속 고부하 시계열 있음.
- 로그 없음 / 중복 배치가 기록된 로그 있음 / 지정 범위의 로그에서 해당 패턴이 발견되지 않음.
- 메모리 89.9% / 90.0% / 90.1%. 수치 조건과 OOM 원인 확정을 별도로 평가.
- 지연 5분 경과 미확인 / 5분 내 회복 / 5분 후에도 초과.
- 두 서비스 중 한 도구 조회 실패 / 관련 매뉴얼 없음 / 추가 조사 한도 도달.
- 미등록 서비스 / 시스템 미지정 / 사용자가 확인해 준 서비스 별칭.

이 사례의 데이터와 테스트 코드는 아직 만들지 않았다. 항상 미확인이라고 답하는 방식으로만 점수를 높이지 않도록, 근거가 실제 제공되는 사례도 함께 평가한다.

## PDF 개선 예시와 연결

- ⑥ 평가 확장: 위 기준의 자동 평가 및 사람 검토. LLM 평가자는 의미 판단을 돕고 수치 조건은 결정론적 검사와 병행한다.
- ⑦ 하드코딩 개선: 시스템 기본값 대체와 단일 매뉴얼 우선순위 선택 개선.
- ⑧ 데이터 보강: 정답과 제공 증거가 명확한 고정 모의 사례 준비.
- ① RAG: 필요할 때 복합 증상 매뉴얼 검색 개선으로 확장. 검색 품질은 별도 측정한다.
- ② 모듈화: 평가·대상 확인·검색 로직을 분리해 테스트 가능하게 구성.
- ③ 전문 에이전트, ④ 사람 승인, ⑤ 장기 대화 압축은 추가 범위이며 이번 문서 작성으로 구현된 기능은 아니다.
